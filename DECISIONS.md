# Decision log

All confirmed with the user. Rationale and alternatives are in

| ID | Decision |
|---|---|
| D1 | Scope as in [PLAN.md](PLAN.md#goal-and-scope): LXD machine controllers plus HA, fresh bootstrap, external PG via URL. |
| D2 | A separate Juju 3.6 controller (name passed in, never hardcoded) deploys `postgresql` 16/stable and `data-integrator` (`database-name=juju`). The PoC uses the scoped user and database this produces, so it has the same privileges a future relation would grant. |
| D3 | One PG database; one PG schema per namespace (`controller`, one per model). One `*sql.DB` per namespace with `search_path` in the connection config. Keep a namespace to (cluster, database, schema) placement indirection so models can be sharded later. |
| D4 | Backend chosen at runtime from agent.conf. Both backends compiled in; dqlite is the default. A separate PG dbaccessor worker is selected in the manifold. |
| D5 | pgx v5 `stdlib` behind an in-tree wrapping `database/sql` driver that rewrites `@sqlair_N` and `?` to `$N`. Long term: upstream sqlair dialect support. |
| D6 | Move the existing schema to `domain/schema/dqlite/` mechanically; generate `domain/schema/postgresql/` with a reusable translator and checked-in per-patch overrides. D12 supersedes the original proposal for a PostgreSQL `triggergen` mode and hand-ported Go triggers: `triggergen` stays unchanged. |
| D7 | SERIALIZABLE isolation everywhere, retry on 40001 / 40P01. change_log writes serialised per namespace with `pg_advisory_xact_lock` in trigger functions. Alternatives documented for later. |
| D8 | TLS is part of the long-term design. The provisioning script deploys plain PostgreSQL by default (`sslmode=disable`) and has an opt-in TLS mode (`self-signed-certificates` on `client-certificates`) that saves the CA to a file and emits `sslmode=verify-full&sslrootcert=<path>`, so TLS overhead can be measured against plain. |
| N1 | Config keys `db-backend` (`dqlite` default, or `postgresql`) and `db-url` (required iff `postgresql`). They flow controller config -> instancecfg -> agent.conf like `dqlite-busy-timeout`. The URL is visible in controller config; acceptable for the PoC only. |
| N2 | Connection details are read through a "connection source" interface (agent.conf backed for now) so a later relation/secret source with credential rotation can replace it. |
| N3 | Plans live in their own repository, `jameinel/juju-4-postgresql-plan` (branch `main`), outside the code branches, so plan updates never force a restack. Amended 2026-10-24; it replaced `docs/implementation-plans/postgresql/` on an integration branch at the bottom of the stack. |
| N4 | PoC branching: stacked `pg-poc/NN-<slug>` branches, worked in one tree and kept current with `git rebase --update-refs` (PLAN.md). The 2026-10-24 change retired the old integration branch and per-stage PoC worktrees. N11 adds an upstream-only worktree exception; it does not restore parallel PoC trees. |
| D9 | The PostgreSQL CA is public, so it is carried in a `db-ca-cert` controller config key (PEM) for the PoC; a relation may supply it long term. `db-backend`, `db-url` and `db-ca-cert` are fixed at bootstrap. |
| D10 | The dqlite schema keeps its declaration order. `pgschemagen` resolves forward references (which SQLite accepts and PostgreSQL rejects) with an ordering pass over the generated DDL ([Stage 4](stages/04-schemagen.md), step 2). Reordering dqlite patches cannot work alone, because model patches depend on each other cyclically (ANALYSIS.md section 4). |
| N5 | Provisioning tooling lives in `scripts/postgresql-poc/`. |
| N6 | Opt-in PostgreSQL tests read the DB URL from `JUJU_POSTGRESQL_TEST_URL`. |
| N7 | The provisioning script is Python using only the standard library (it shells out to `juju ... --format=json`), runnable with plain `python3`. |
| N8 | The stages form one linear stack in numeric order on upstream `4.1` (`a8591fe1b8`): 00 -> 01 -> 02 -> ... -> 10. Amended 2026-10-24; it replaced a stack with side branches (01 on 00; 04 and 05 both on 03; 07 on 00), which have all been restacked into the line. |
| D11 | `domain/schema.Backend` selects `ControllerDDLForBackend` / `ModelDDLForBackend`; existing `ControllerDDL()` / `ModelDDL()` stay dqlite. `Schema` carries a `core/database/dialect.Dialect` interface (leaf package, no Juju imports) with `dialect.SQLite` / `dialect.PostgreSQL` bookkeeping implementations. `schema.New` defaults to SQLite; `NewForDialect` takes a dialect; the harness exposes `SchemaDialect()`. Stage 8 wires backend selection into bootstrap, tracker and upgrade worker. The leaf interface supersedes the schema-local enum to avoid a harness import cycle; [history](history/schema-generation.md#dialect-and-change-log-corrections). |
| D12 | `pgschemagen` reads the complete dqlite patch list (`ControllerDDL()` / `ModelDDL()`, SQL files plus Go-built triggers) and translates every trigger generically to a PL/pgSQL function and trigger. `triggergen` gets no PostgreSQL mode and the Go-built triggers are not ported by hand (replaces Stage 4 steps 3 and 4). |
| D13 | A `BEFORE INSERT` trigger on `change_log` takes `pg_advisory_xact_lock` keyed on its schema, then assigns generated IDs so they become visible in commit order (D7). `change_log.id` is plain `BIGINT` with owned `change_log_id_seq`; draw `nextval` only for null IDs and advance past explicit IDs to preserve fixtures. This replaced identity defaults evaluated before the trigger; [history](history/schema-generation.md#dialect-and-change-log-corrections). The generated-ID ordering guarantee does not by itself cover arbitrary explicit-ID insertion during live streaming. |
| D14 | Types: `INT` / `INTEGER` -> `bigint`; `AUTOINCREMENT` -> `bigint GENERATED BY DEFAULT AS IDENTITY`; `DATETIME` / `TIMESTAMP` -> `timestamptz`; `STRFTIME` / `DATETIME('now')` -> `now()`; `BOOLEAN` -> `boolean`; `BLOB` -> `bytea`; `user` is quoted. Identifiers over 63 bytes are shortened with a hash suffix. |
| D15 | Generated, checked-in `domain/schema/postgresql/<ns>/sql/NNNN-<slug>.sql`, one per dqlite patch, embedded by `domain/schema`. A hand tweak lives in `<ns>/overrides/` as `NNNN-<slug>-auto.sql` (raw translator output, rewritten every run) plus a hand-maintained `NNNN-<slug>.diff` (unified diff, auto -> desired) applied before the ordering pass. A hunk that no longer applies, or a diff with no patch, fails generation. A test checks the generated files are up to date. |
| D16 | Stage 5 query fixes: lease and lease-expiry times are computed in Go and bound as `YYYY-MM-DD HH:MM:SS` UTC text (the values SQLite stored before); plain "now" columns use `CURRENT_TIMESTAMP`; `GROUP_CONCAT` in `GetUnitsK8sPodInfo` is replaced by aggregating rows in Go, with no dialect hook; `PRAGMA defer_foreign_keys` is left for Stage 4 / 6 (recorded in Stage 5 findings). |
| D17 | PostgreSQL constraint tag, space and zone tables get explicit identity `rowid` columns, preserving the insertion order used by `v_application_constraint`. Keep inserts column-qualified. The dqlite definitions are unchanged. |
| D18 | `v_revision_updater_application_unit` groups by `a.uuid`, returning one actual unit count per application. This initially required a PostgreSQL override for the dqlite `GROUP BY u.uuid` bug. At the user's request, Stage 4 subsequently incorporated the shared schema fix and removed the obsolete override. The current 4.1 beta base schema changes in place; supported 4.0-to-4.1 moves use a fresh controller and model migration, not an in-place controller upgrade. |
| D19 | Stage 8 worker shape: a separate `pgWorker` in `internal/worker/dbaccessor`, selected in the manifold from `connsource` details and reusing `trackedDBWorker`. It has no node lifecycle, HA or handover logic; `ClusterDescriber` is a no-op. |
| D20 | Each namespace lives in schema `"juju_" + namespace` (`juju_controller`, `juju_<model-uuid>`), always with the underscore, built by one function (`postgresql.Placement.SchemaName`). Tests may override the prefix so they never touch `juju_controller`. |
| D21 | Bootstrap takes one `agentbootstrap.DatabaseInitialiser` interface. The jujud bootstrap command, as composition root, selects the dqlite or PostgreSQL implementation from `connsource`. |
| D22 | The PostgreSQL CA (`db-ca-cert`) is applied in memory with `postgresql.WithRootCAs`, which errors unless the URL uses `sslmode=verify-ca` or `verify-full`. No `sslrootcert` file is written. |
| D23 | One PostgreSQL database per controller. Bootstrap fails fast if the controller or controller model schema already exists; restore is future work. A script to drop `juju_*` schemas supports repeated PoC bootstraps. |
| N9 | PostgreSQL test schemas are named `juju-test-<pid>-<n>[-<suffix>]`, carry a `COMMENT ON SCHEMA` with the PID, start time and test name, and are quoted with `pgx.Identifier`. Once per process the harness drops test schemas whose PID is gone. |
| N10 | Backend-only test skips use `SkipOnPostgreSQL` with a "dqlite only: <reason>" message, called before `SetUpTest`. |
| N11 | Dedicated worktrees are allowed for concurrent upstream-only 4.1 review branches. Give each branch/worktree one owner. UPSTREAM-PLAN.md is a standalone stock-4.1 implementation/QA guide; it requires no PoC checkout, setup or validation. UPSTREAM-FIXES.md owns evolving findings/provenance/status; UPSTREAM-INTEGRATION.md owns the reusable reintegration procedure. PoC implementation/restacking stays in its single tree. |
| N12 | Add the relation-status integer fix U12 as a separate commit to the existing `4.1-sqlite-integers` branch, which already contains U1/U2 and the legacy-ID parsing helpers. Do not create a duplicate U1 branch or a separate U12 review branch. |
| D24 | The change stream (DIALECT.md X16) selects the latest change per namespace and changed value with a `MAX(id)` CTE joined back to `change_log`, not bare columns. |
| D25 | `TestTxnLogging` is skipped on PostgreSQL (N10) rather than emitting tracer spans from the pgx wrapper; tracing is future work. |
| D26 | The PostgreSQL driver decodes `timestamptz` in UTC on every connection (DIALECT.md X14). |
| D27 | Columns holding raw random bytes (activation key, bakery keys, macaroon root key) become `BLOB` in the dqlite schema, generating `bytea` (U8, DIALECT.md X11). |
| D28 | `v_model_config` prefers the `agent_version` values for `agent-stream` and `agent-version` and uses `UNION ALL` (U7, DIALECT.md X15). |
| D29 | `constraint.allocate_public_ip` stays `INT` in dqlite; a PostgreSQL override makes it `BOOLEAN`, and status reads it as `sql.Null[bool]` (DIALECT.md X25). |
| D30 | Where a dqlite column's declared type disagrees with what every writer binds, correct the 4.1 beta base schema in place, regenerate, and add a 4.0.12 import delta: `removal.force` becomes `BOOLEAN` (U9), and `relation_status_type.id` and `relation_status.relation_status_type_id` become `INT` (U12), in both schemas rather than via a PostgreSQL override. Existing beta PoC databases must be recreated. |
| D31 | `GetBlocks` orders by `block_command_type_id` instead of `rowid` (DIALECT.md X31); dqlite order changes from insertion order to type order. |
| D32 | Production `IIF` becomes `CASE` (DIALECT.md X7). |
| D33 | Operation prune sizes use `octet_length(CAST(x AS TEXT))` (DIALECT.md X33). A stored-bytes measure (`pg_column_size` or page-based) is an upstream follow-up, because state code has no backend awareness. |
| D34 | Boolean parameters are compared with `FALSE` / `TRUE`, not `0` / `1` (DIALECT.md X34). |
| D35 | The crossmodelrelation secrets queries (DIALECT.md X16, X30; U11) need dedicated semantic review and multi-unit tests because fixing them changes dqlite behaviour. Originally deferred; D40 supersedes that scheduling decision and requires the fix before the PoC is functional. Candidate semantics are not yet approved; see [investigation](investigations/crossmodel-secrets.md). |
| D36 | New row ids are read with `INSERT ... RETURNING`, not `sql.Result.LastInsertId`, which pgx does not support (DIALECT.md X35). Verified on dqlite, SQLite and PostgreSQL through `database/sql` and sqlair. |
| D37 | `putMetadata` uses one untargeted `ON CONFLICT DO NOTHING` instead of one clause per hash (DIALECT.md X36). The only other unique key is the uuid primary key, so a reused uuid returns `ErrHashAndSizeAlreadyExists`. |
| D38 | Compare three cases: stock upstream Juju at a recorded revision, the PoC using dqlite, and the PoC using PostgreSQL. The two PoC cases use the same source revision. Record build and deployment configurations; these compare Juju implementations, not database engines in isolation. The aim is to upstream most dqlite-side changes, so pin and report the upstream baseline as fixes land. Workload details remain open in [BENCHMARKS.md](BENCHMARKS.md). |
| D39 | Start with functional single-controller deployments and the first three-way comparison; Juju controller HA remains in scope as a subsequent milestone. |
| D40 | Cross-model relation secrets fixes (U11) must be implemented before the PoC is considered functional. Give them a dedicated design/fix task rather than incidental test cleanup. PostgreSQL model import/export is deferred; this does not waive upstream import/export compatibility tests for shared 4.1 fixes. |
| D41 | Stage 10 is Juju controller HA over one writable PostgreSQL primary. It checks concurrent controllers and controller loss/rejoin, not read-replica routing or PostgreSQL primary failover. |

Before Stage 8 implementation: dual-backend driver/schema/harness/bootstrap, lease/change-stream/controller-node checks; finish X37/X38; triage unexplained status failures and resolve runtime blockers. Broader application/machine/removal coverage and the U11 cross-model fix remain required before the functional milestone, but need not all precede worker implementation. PostgreSQL import/export stays deferred under D40. |
