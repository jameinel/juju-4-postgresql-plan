| D47 | Production PostgreSQL `DeleteDB` never uses CASCADE. Unexpected objects or dependents outside the schema fail the delete with PostgreSQL's dependency detail; the undertaker logs the error and retries. Deleting a schema that does not exist succeeds. The delete uses a short-lived admin pool. The test harness keeps its own per-test schema cleanup. Amended 2026-10-27 (08-delete): the transaction uses READ COMMITTED, an exception to D7. | D53 | Every PostgreSQL schema change transaction runs the dialect's `BeginSchemaChangeSQL` before any query: `SET TRANSACTION ISOLATION LEVEL READ COMMITTED`, then `pg_advisory_xact_lock` on a fixed key (the bytes of `juju_ddl`), held until the transaction ends. SQLite returns no statements. `Schema.Ensure` runs them first (bootstrap, tracker creation, upgrades and the test harness); `DeleteSchema` runs them after `SET LOCAL lock_timeout`. So only one Juju schema change runs at a time on each database, and D47's single transaction is kept. One model create takes about 3,600 locks and one delete about 4,400, against a shared table of 8,768 (X42). READ COMMITTED is an exception to D7: a SERIALIZABLE `Ensure` running for a second or more pins the predicate locks of every concurrent SERIALIZABLE transaction and exhausted that table under load (X43). It also lets a transaction that waited for the lock see the changes of the one it waited for (X39). The user asked for minimal exposure, so the dialect has one opaque method and runners are unchanged. Confirmed 2026-10-28 (08-delete-locks). Cost, measured 2026-10-28: READ COMMITTED none; the lock makes parallel PostgreSQL test packages queue for schema setup, because the harness puts every test schema in one database (three packages in parallel: +20% batch time; [08-delete-locks result](stages/08-dbaccessor.md#08-delete-locks-result), Stage 6 task 06-test-speed).
