| D44 | A model namespace has a single initialiser; Stage 8 adds no lock. The creating request makes the first `GetDB` before activation, model workers and API logins wait for activation, and each controller runs one tracker per namespace. On PostgreSQL a namespace is initialised when its `schema` bookkeeping table in `juju_<ns>` exists with at least one version row, checked through `pg_catalog`; schema existence alone is not enough. The tracker applies the full model DDL only when that marker is absent; incremental patches stay with the upgrade worker. Ensure runs in one transaction, so a failed create leaves an empty schema and a rare overlap returns a `GetDB` error that is retried. Runtime never creates the controller schema or applies its DDL; a missing controller marker is an error. |
| D45 | A PostgreSQL controller registers its `controller_node` row by calling the existing `AddDqliteNodeID(controllerID)` at worker start, before serving requests. This replaces dqlite's `AddDqliteNode` upsert, which is the only source of rows for machine HA controllers. The dqlite-flavoured name stays for the PoC. |
| D46 | Provisional: the PostgreSQL tracker ping also checks that a model namespace's schema still exists. If the schema is gone, the tracker exits with `ErrDBDead`, so pools on other HA controllers close after a `DeleteDB`. Without this, each deleted model would leave up to 3 idle connections per other controller until restart. A different mechanism, such as a namespace-removal notification, may replace this check later. Amended 2026-10-26 by D50; it applied to every namespace, including the controller's. |
| D47 | Production PostgreSQL `DeleteDB` never uses CASCADE. In one transaction with `SET LOCAL lock_timeout` (15 s), it lists the schema's objects from `pg_catalog` and drops views, then tables (which removes their indexes, triggers and owned sequences), then functions (by `regprocedure`), then any remaining sequences, then the schema, all with RESTRICT. Unexpected objects or dependents outside the schema fail the delete with PostgreSQL's dependency detail; the undertaker logs the error and retries. Deleting a schema that does not exist succeeds. The delete uses a short-lived admin pool. The test harness keeps its own per-test schema cleanup. Amended 2026-10-27 (08-delete): the transaction uses READ COMMITTED, an exception to D7. Under a SERIALIZABLE snapshot, objects dropped concurrently are still listed, and `regclass` renders their missing OIDs as bare numbers, so the `DROP` statement fails with a syntax error. SSI does not track catalog reads, so SERIALIZABLE adds no protection here (DIALECT.md X40). Amended 2026-10-28 (08-delete-locks): the delete first takes the schema change lock (D53), bounded by its `lock_timeout`. |
| D48 | The tracked database (`internal/worker/dbaccessor/tracker.go`) takes two interfaces and has no backend conditionals. `DBOpener` (`Open(ctx, namespace)`) replaces the `DBApp` parameter; `DBApp` embeds it, so dqlite callers are unchanged. `TrackedDBBackend` (`PrepareDB`, `EnsureModelInitialised`, `Ping`), set with `WithBackend`, defaults to dqlite (foreign keys pragma, `sqlite_master` check, `ModelDDL()`, plain ping). One Placement-backed type, `PostgresNamespaces`, implements both for PostgreSQL. A ping error satisfying `ErrDBDead` ends the tracker without reopening, so a removed schema is never recreated; dqlite never returns it from a ping. |
| D49 | The dbaccessor `ManifoldConfig` takes a `DBConnectionSource connsource.Source` (N2). `Start` reads its details and starts the dqlite worker or `pgWorker` (D4, D19); any other backend is an error, and the PostgreSQL path needs none of the dqlite inputs. The machine and safe mode agents pass their controller startup value providers, which read the current agent config. |
| D50 | Losing the PostgreSQL controller schema at runtime is fatal to `pgWorker`. Juju never deletes it, so the controller tracker's ping returns a plain error rather than `ErrDBDead` (amending D46). Once the tracker's reopen attempts also fail, the runner treats the error as fatal and the worker fails. On restart, the controller marker check (D44) keeps failing until an operator restores the schema. |
| D51 | The upgradedatabase `ManifoldConfig` takes the same `DBConnectionSource connsource.Source` as dbaccessor (D49), and the machine agent passes the same startup value provider, so both workers read the backend from one source. A controller never changes backend during an upgrade; changing backend means a new controller and a model migration. `Start` maps `controller.DBBackendDqlite` / `DBBackendPostgreSQL` to `schema.Backend` with an explicit switch and rejects any other backend before the worker starts. The worker `Config` carries the resolved `schema.Backend`, validates it, and applies `ControllerDDLForBackend` / `ModelDDLForBackend` (D11). |
| D52 | The PoC cleanup tool, `scripts/postgresql-poc/drop-juju-schemas.py` (Stage 8 task 08-cleanup-tool), lives on Stage 1 beside the provisioning script, so every later stage carries it. It runs `psql` with the URL split into `PG*` environment variables and never prints the URL. With no options it only prints an inventory. It covers Juju schemas (`juju_controller`, `juju_<model uuid>`, and any other `juju_*` name, listed as unknown) and the test harness's `juju-test-<pid>-<n>...` schemas. Dropping needs exactly one of `--controller UUID`, `--schema NAME` (several `juju_*` names, or one test schema) or `--stale-test-schemas`, then a typed confirmation or `--yes`. Unlike D47 it drops with CASCADE, guarded by a check that nothing outside the targets depends on them, which each drop transaction repeats. Each schema is dropped in its own transaction, with `juju_controller` last, because one model schema takes about 4,400 locks from the cluster-wide lock table (X42). Juju schemas are dropped only when every LXD instance (in any project) of the database's controller and models is stopped, and `lxc` must work. Test schemas are dropped only when their process has gone or its PID now belongs to a later process. Nothing runs the tool automatically, and it has no option to drop everything: a failed bootstrap may have found another controller's database (D23). Confirmed 2026-10-27; the per-schema transactions replaced a single transaction after the lock measurements. |
| D53 | Every PostgreSQL schema change transaction runs the dialect's `BeginSchemaChangeSQL` before any query: `SET TRANSACTION ISOLATION LEVEL READ COMMITTED`, then `pg_advisory_xact_lock` on a fixed key (the bytes of `juju_ddl`), held until the transaction ends. SQLite returns no statements. `Schema.Ensure` runs them first (bootstrap, tracker creation, upgrades and the test harness); `DeleteSchema` runs them after `SET LOCAL lock_timeout`. So only one Juju schema change runs at a time on each database, and D47's single transaction is kept. One model create takes about 3,600 locks and one delete about 4,400, against a shared table of 8,768 (X42). READ COMMITTED is an exception to D7: a SERIALIZABLE `Ensure` running for a second or more pins the predicate locks of every concurrent SERIALIZABLE transaction and exhausted that table under load (X43). It also lets a transaction that waited for the lock see the changes of the one it waited for (X39). The user asked for minimal exposure, so the dialect has one opaque method and runners are unchanged. Confirmed 2026-10-28 (08-delete-locks). |
| N13 | Tests follow the code repository's AGENTS.md wait rule: block on an event that must happen, with no explicit timeout branch, and rely on the go test timeout. Runs supply the bound instead: every test run gets a short `-timeout` (about 120 s), and nothing an agent starts goes more than about two minutes without a progress check. Split work into package-, suite- or test-group-sized runs; a run that cannot be split gets an agreed budget and periodic checks ([OPERATIONS.md](OPERATIONS.md#bounded-runs-and-check-ins)). Considered and not adopted (2026-10-27): `LongWait` select branches, and a deadline-context helper. `tc.C.Context()` is `testing.T.Context()`, cancelled only after the test function returns, so a deferred `workertest` kill of a worker whose goroutine has died blocks until the go test timeout. |
| N14 | `pgtesting.URL()` appends `lock_timeout=30s`, `statement_timeout=60s` and `idle_in_transaction_session_timeout=60s` to the PostgreSQL test connection string unless it already sets them, so a blocked test session fails with a PostgreSQL error before the go test timeout. Every PostgreSQL test connection reads its URL there; production connections are unaffected. A transaction's own `SET LOCAL` (D47) overrides them. Implemented on Stage 6 (`06=4615e24467`). |
| N15 | The per-test PostgreSQL schema teardown (`pgtesting.CreateSchema` and `DropSchemasOnCleanup`) still drops with CASCADE, so the database is clean for later tests. First it lists from `pg_depend` every object outside the schema that depends on the schema or an object in it; if there are any, the test fails, naming each dependency. An object is inside when its catalog row names the schema (default privileges in the schema included) or it belongs to an inside relation or operator family. Internal dependents, such as TOAST tables, are part of their object. Objects in unlisted catalogs count as outside, so a gap fails a test rather than hiding a leak. Between two schemas dropped by one `DropSchemasOnCleanup`, a dependency counts as outside. The query needs no extension and takes about 15 ms. The process-start sweep (N9) still only logs. Implemented on Stage 6 (`06=e7f3822281`). |
