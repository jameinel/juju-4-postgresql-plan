# SQLite and PostgreSQL differences

Behaviour that differs between dqlite (SQLite) and PostgreSQL and that
Juju code depends on. Each entry gives what each backend does, where Juju
hits it, and how the PoC handles it. Cite entries by id (X1, X2, ...).
Add an entry for every new difference found, including ones only
worked around. Keep the id when its handling changes.

Verified on SQLite 3.45.1 and PostgreSQL 16.15 on 2026-10-24 unless an
entry says otherwise. Schema-only differences handled by `pgschemagen`
are summarised in section 4 rather than listed one by one.

Handling states:

- **Shared fix**: one query or DDL valid on both backends.
- **Driver rewrite**: the Stage 3 driver (`internal/database/postgresql`)
  rewrites SQL that sqlair or callers produce. This is a PoC workaround;
  long term the query layer should emit dialect-correct SQL (D5:
  upstream sqlair dialect support), or callers should avoid the
  construct.
- **Generator**: `pgschemagen` translates it (Stage 4).
- **Open**: seen, not yet handled.

For shared findings, use D55 and the
[upstream SQL/schema contract](UPSTREAM-PLAN.md#purpose-and-sqlschema-acceptance).
Determine whether the declared storage type and query semantics are correct
before adapting a bind, scan, driver rewrite or generated override. A PoC
workaround can unblock execution without resolving the shared defect.
Conversely, genuine dialect translation stays in the PoC; upstream 4.1
fixes must not gain PostgreSQL-specific SQL or support dependencies.

## 4. Schema and DDL (generator)

Handled by `pgschemagen` (Stage 4; D10, D12, D14, D15). Detail in
ANALYSIS.md section 4.

- Forward references: SQLite resolves `REFERENCES` and view sources on
  use; PostgreSQL at `CREATE`. Reordered by the generator (D10).
- A foreign key target must be a primary key, unique constraint or
  non-partial unique index when the key is created.
- `INTEGER PRIMARY KEY AUTOINCREMENT`, `STRICT`, `IIF`, `strftime`
  defaults.
- Triggers: SQLite `BEGIN ... END` bodies, `RAISE(ABORT | FAIL, ...)`
  and `WHEN` become PL/pgSQL functions with `RAISE EXCEPTION`.
  PostgreSQL does not allow subqueries in a trigger `WHEN`
  (`schematesting.FailingTriggerSQL`, Stage 6).
- PostgreSQL evaluates column defaults before `BEFORE` triggers (D13).
- Identifiers over 63 bytes are truncated by PostgreSQL; the generator
  adds a hash suffix (D14).

D55 audit (2026-11-06): not every generator rewrite is a dialect
difference. These are valid on SQLite too, so the shared schema should
change and the rewrite or override should then be removed. Each is an
UPSTREAM-PLAN.md candidate:

- `IIF` in view bodies (`rewriteExpr`); use `CASE`. The only schema use
  is `v_model_all` (`controller/sql/0007-model.sql`), already covered by
  #23751. `rewriteExpr` also handles `IFNULL`, which the schema no longer
  uses.
- Bare `user` table references (quoted by `rewriteExpr`; X8).
- `BOOLEAN` defaults written as `0` / `1` (`booleanDefaults`). One
  remains at `148e09f015`: `flag.value` (`controller/sql/0016-flag.sql`).
  `translateInsert` also converts `0` / `1` in seed rows for `BOOLEAN`
  columns; which seeds rely on it has not been audited.
- Overrides: predicate-free joins (X29), `v_user_last_login` (X16),
  implicit `rowid` order (X31, D17), `allocate_public_ip` (X25) and the
  duplicate constraint name `fk_offer_connection_uuid` on
  `application_remote_consumer` (`0034-cross-model-relation.sql`; one
  key targets `application`, the other `offer_connection`). SQLite
  accepts duplicate constraint names within a table (checked with
  sqlite3); PostgreSQL rejects them. The Stage 4 override renames the
  first to `fk_offer_connection_application_uuid`.

Genuine differences (keep in the generator): type names, `STRICT`,
`WITHOUT ROWID`, `AUTOINCREMENT`, trigger bodies, forward references,
identifier length.

Tentative (D56): `STRFTIME('%Y-%m-%d %H:%M:%f', 'NOW', 'utc')` column
defaults (seven sites). The PoC uses `CURRENT_TIMESTAMP`. Changing
upstream to it is a possibility, not a commitment: on SQLite it drops
millisecond precision, which nothing currently needs but which costs
little to keep. On PostgreSQL, `CURRENT_TIMESTAMP` is `now()` and keeps
microseconds. Sub-second precision is unused at six sites:

- `change_log.created_at` (controller and model): every generated
  trigger writes whole-second `DATETIME('now', 'utc')`, and the stream
  scans the value without using it.
- `change_log_witness.updated_at` (controller and model): the stream
  writes `DATETIME('now', 'utc')`; only export reads it.
- `removal.scheduled_for`: every production insert binds it from Go.
- `machine_requires_reboot.created_at`: the default applies, but only
  export and import read it.

The exception is `charm.create_time`. The default applies
(`setCharmState` omits it), and `GetLatestPendingCharmhubCharm` returns
the first row of `ORDER BY create_time DESC`. A millisecond timestamp
does not guarantee a unique order, and PostgreSQL `now()` is the
transaction start time. This is a separate ordering candidate whatever
the default becomes.

`CURRENT_TIMESTAMP` is always UTC on SQLite and stores the same
`YYYY-MM-DD HH:MM:SS` text as `DATETIME('now', 'utc')`, which the stream
and `Watermark` already write and scan into `time.Time`. Checked with
sqlite3 3.46.1 under three `TZ` values. The current form relies on
`'utc'` after `'now'`, which SQLite documents as undefined but has
treated as a no-op since 3.10.0; dqlite builds 3.47.0
(`scripts/dqlite/scripts/env.sh`). Existing `.SSS` rows and new

## 5. Transactions, errors and connections

| Id | Behaviour | SQLite / dqlite | PostgreSQL | Handling |
|---|---|---|---|---|
| X18 | Error inside a transaction | Many constraint errors undo only the statement; conflict policy can differ | A statement error aborts the transaction unless recovered through a savepoint | Shared fix per site: avoid expected conflicts in SQL. `PinLease`, `RequireMachineReboot`, `AllowCloudType` and the unit net node insert use `ON CONFLICT DO NOTHING`; `EnsureExternalUser` checks first (Stage 5). SERIALIZABLE does not universally turn a concurrent unique conflict into 40001: 23505 remains possible depending on all writer paths. See [PostgreSQL's isolation contract](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-SERIALIZABLE). Verify the actual concurrent writers before relying on retry classification; do not blindly retry every constraint error. |
| X19 | Isolation | One writer at a time | SERIALIZABLE; 40001 / 40P01 at any statement or `COMMIT` | D7; retried by `drivererrors.IsErrRetryable` (Stage 3). Schema change transactions use READ COMMITTED (D53, X43). |
| X20 | Constraint errors | SQLite extended codes | SQLSTATE 23xxx; unique and primary key share 23505 | Mapped in `drivererrors` (Stage 3). |
| X21 | Foreign keys | Off unless `PRAGMA foreign_keys`; `PRAGMA defer_foreign_keys` | Normally enforced; SQL deferral needs `DEFERRABLE` keys and `SET CONSTRAINTS` | Harness requires enforcement. PostgreSQL model import/export is deferred (D40): `domain/modelimport/state/model/import.go` uses `PRAGMA defer_foreign_keys = 1`. A future design must cover generated FK declarations (including relocated FKs) and import transaction semantics together; adding `SET CONSTRAINTS` alone is insufficient. `domain/recovery/state` replays dqlite dumps using deferral/check PRAGMAs and remains dqlite-only. Machine reprovision test checks need a separately justified backend-specific assertion (Stage 6), not blanket removal of FK coverage. |
| X22 | Connections | In-process, cheap | Server `max_connections` (100 on the PoC server); an unbounded `database/sql` pool can exhaust it | `dbaccessor` `applyDBLimits` caps each tracked pool at 3 connections for any opener, so the Stage 8 PostgreSQL tracker (`PostgresNamespaces`, D48) gets the same cap. The Stage 6 harness applies it to PostgreSQL test pools. |
| X35 | `sql.Result.LastInsertId` | Returns the connection's last inserted rowid, even when the statement inserted no row | pgx: "LastInsertId is not supported by this driver" | Shared fix (Stage 5, `fix(keymanager): return new public key ids from the insert`): `INSERT ... | X39 | Concurrent `CREATE TABLE IF NOT EXISTS` of the same table | dqlite has one writer, so the second transaction sees the committed table and skips it | Transactional DDL: the second waits for the first, then fails with 23505 on `pg_type_typname_nsp_index`, or with 42P07 "relation already exists" if it started after the commit. Neither is retryable. | Accepted under D44: model DDL has a single initialiser, and an overlap is rare. In the Stage 8 overlap test (4 trackers on one fresh namespace) 3 failed with these errors, left no marker, and each retry succeeded. `EnsureSchema` runs outside a transaction and already tolerates the schema-creation race. | X40 | Catalog reads in a SERIALIZABLE transaction | One writer, so the schema a transaction reads is the schema its DDL changes | `pg_catalog` queries read the transaction's snapshot, but DDL and the `regclass` / `regprocedure` output functions use the current catalog. An object dropped by a transaction that commits after the snapshot is still listed, and its OID renders as a bare number, so a generated `DROP` fails with a syntax error. SSI does not track catalog reads, so no 40001 is raised. | `postgresql.DeleteSchema` uses READ COMMITTED, so each listing takes a new snapshot (D47 amendment, an exception to D7; Stage 8). The other catalog readers (`SchemaExists`, `SchemaInitialised`) only test existence and render no names. |
| X41 | Deleting a namespace | dqlite: `PRAGMA delete_database` removes the whole database, whatever it holds (`internal/database/deletedb_linux.go`) | `DROP SCHEMA ... An aggregate is reported there as a function. | D47 (Stage 8, 08-delete): `postgresql.DeleteSchema` drops Juju's object kinds (views, tables, functions, sequences) by name, then the schema, all with RESTRICT. Anything else, or any outside dependent, fails the delete and nothing is dropped. `postgresql.DropSchema` (CASCADE) is for tests only. |
| X42 | Locks taken by deleting a namespace | dqlite: `PRAGMA delete_database` removes one database, with no per-object locks | Every dropped object takes an AccessExclusive lock, held until commit and never fast-path. That includes each table's TOAST table and index and its row and array types, each index and constraint, the 4 internal triggers of each foreign key, and each trigger, function, view rule and default. Each lock uses a slot in a shared lock table sized `max_locks_per_transaction × (MaxBackends + max_prepared_transactions)`, shared by every session in the cluster. On PostgreSQL 16, MaxBackends is `max_connections + autovacuum_max_workers + 1 + max_worker_processes + max_wal_senders`, so the PoC server's table is 64 × 137 = 8,768 (6,400 was recorded before 2026-10-28). The hash table can borrow spare shared memory, so the limit is soft. When the table is full, any session's next lock fails with 53200 `out of shared memory`. Measured 2026-10-27 at 156 model patches: one model schema takes 4,421 locks with CASCADE and 4,428 with `DeleteSchema`'s RESTRICT sequence; `juju_controller` takes 1,473. Foreign keys account for 36% (317 constraints and 1,268 triggers), tables for 28% (251 × 5) and change-log triggers with one function each for 13% (292 × 2). Controller and 2 models in one transaction (10,303 locks) succeeded on spare shared memory; controller and 5 models failed. | Done: Stage 8 task 08-delete-locks (D53). Every Juju schema change transaction takes a per-database advisory lock first, so one model delete (4,418 locks, about 50%) or create (3,628, about 41%) runs at a time on each database. The cleanup tool drops one schema per transaction (D52). |
| X43 | Predicate locks of long transactions | One writer and no SSI bookkeeping | SERIALIZABLE transactions take SIRead locks in a server-wide table sized from `max_pred_locks_per_transaction` × MaxBackends (8,768 targets on the PoC server). A committed transaction's SIRead locks are kept until every transaction that overlapped it has ended, so one long SERIALIZABLE transaction pins the locks of every SERIALIZABLE transaction that commits meanwhile, across all schemas. When the table is full, any SERIALIZABLE statement fails with 53200 and the hint "increase max_pred_locks_per_transaction". | D53 (Stage 8, 08-delete-locks): schema change transactions run at READ COMMITTED. Measured 2026-10-28: with model creates (about 1.1 s each) at SERIALIZABLE beside two readers of every table of another model, creates and readers failed (peak 17,536 SIRead rows). With four readers of 10 tables each the peak was about 13,700; at READ COMMITTED it was 830. Two readers of every table still fail with no schema changes running, so heavy SERIALIZABLE reads can exhaust the table on their own (Stage 11 READ COMMITTED experiment). |
